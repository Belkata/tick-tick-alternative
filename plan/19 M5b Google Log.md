## Slices
1. ✅ **Cache and mappings, no network** (2026-11-25). `core/src/gcal.rs`, schema **v8** (`008_gcal.sql`).
   - `gcal_calendar` and `gcal_event` are plain per-device tables, not ops, so nothing syncs over P2P.
   - `task_event_id`: UUID in base32hex (26 chars, a–v and 0–9) for deterministic event ids.
   - `task_event_body`: a task as a Google event (✓ prefix when done, all-day uses `date` with an exclusive end, `tt_task_id` in private extended properties). Repeats are **not** expanded yet.
   - `GcalEventUpdate::parse`: one `events.list` item to upsert or remove. Hides cancelled, working-location, out-of-office, focus-time and our own pushed events.
   - `Store::gcal_set_calendars`, `gcal_select`, `gcal_calendars`, `gcal_sync_token`, `gcal_apply` (full resync clears first; the token is saved in the same transaction), `gcal_events(from, until, tz)`.
2. ✅ **HTTP client and OAuth (desktop)** (2026-11-26), new crate `google/` (`tt-google`). Tested against a fake local Google, so no real sign-in has run yet.
   - `oauth`: loads Google's `client_secret_*.json` (kept in `~/.config/utre/google-client.json`, never in the repo), PKCE S256 (RFC 7636 test vector), a one-shot `127.0.0.1` loopback listener that checks `state`, code exchange and refresh. Scopes: `calendar.readonly` and `calendar.app.created`.
   - `tokens`: `TokenStore` trait with `FileTokenStore` (owner-only file, atomic write). **Deviation from plan/06:** tokens are in a file for now, not the OS keychain. The `keyring` crate's 4.x API needs checking first; the trait lets it slot in later.
   - `session`: `sign_in(open_browser)`, `access_token` (refresh 60 s early, one refresh at a time; a revoked refresh token clears the tokens and answers `SignedOut`), `get_json` (one forced refresh on 401, back-off on 429, rate-limit 403 and 5xx, 410 becomes `Gone`).
   - `calendar`: `list_calendars`, `sync_events` (window -30/+365 days with `singleEvents=true`, then `syncToken`; 410 falls back to a full fetch), `sync_calendars(session, store, now)` fills the cache for selected calendars.
   - Versions (checked 2026-11-26): reqwest 0.13.5 (already in the lockfile via iroh), sha2 0.11, base64 0.23, getrandom 0.4, url 2.5, tokio 1.54.
   - Wired into the daemon (2026-11-26, `daemon/src/google.rs`): `GoogleStatus`, `GoogleSignIn`, `GoogleSignOut` and `GoogleSync` requests on the socket (the same control hook as sync), a fetch every 5 minutes while signed in, `--no-google`. The cache is also readable through the `api!` table (`gcal_calendars`, `gcal_select`, `gcal_events`). CLI: `tt google status | sign-in | sign-out | sync | calendars | select | events`.
   - **Real sign-in tested** (2026-11-26, throwaway daemon and DB): the browser flow worked, 14 calendars listed, one selected, its events fetched (35 cached) and the second fetch used the saved sync token. The token file is owner-only.
   - Still to do for this slice: the app's Google button and calendar picker (slice 3), "on window focus" fetch (the app calls `GoogleSync`), and the keychain for tokens.
3. ✅ **Events in on the calendar** (2026-11-26). Desktop only: the phone has no daemon, so it has no Google yet (slice 5).
   - Bridge (`TaskDb`): `googleAvailable`, `googleStatus`, `googleSignIn`, `googleSignOut`, `googleSync`, `gcalCalendars`, `gcalSelect`, `gcalEvents` (mirrors of `GoogleStatus`, `GcalCalendar`, `GcalEvent`; bindings regenerated).
   - Calendar (`app/lib/calendar/calendar_page.dart`): `GoogleEvent` is a read-only `KalenderEvent` (no drag, resize or drop), loaded with the tasks on every reload, so the daemon's fetches show live through the change stream. A paler tint than a task block, a hollow dot in Month. A tap opens a dialog (title, time, calendar name, "Copy link"); there is no "Open in Google Calendar" button because the app has no URL-launcher dependency yet.
   - Page (`app/lib/desk/google.dart`, sidebar entry "Google Calendar"): not set up / sign in (with a "copy the sign-in link" fallback) / signed in with "Fetch now", "Sign out" (asks first) and a switch per calendar (turning one on fetches at once).
4. ✅ **Tasks out** (2026-11-26; tested against the fake Google only, no real push yet). Code: `google/src/push.rs`, `core/src/gcal.rs` (`gcal_push_plan`), `daemon/src/google.rs`.
   - **Off until switched on**, per device (`meta.gcal_push`, never synced): the Google page's "Send timed tasks to Google" switch (it also sends all-day tasks, as decided in plan/11 #6), `utre google push on|off`, `push-status`, `push-now`. Requests: `GooglePushStatus`, `GooglePushNow` (daemon control), `gcal_push_enabled`/`gcal_push_set` in the `api!` table. Bridge additions: `googlePushEnabled/Set/Status/Now`.
   - **The calendar**: a secondary calendar "Tasks" with a marker in its description. The id is remembered per device (`meta.gcal_tasks_calendar`, dropped on sign-out). With no id the device looks for a calendar with that name and marker before creating one, so a second device reuses the first one's. If it was deleted on Google (404), a new one is made.
   - **Reconcile = diff of a plan against one `events.list`.** The plan is `Store::gcal_push_plan(now)`: every open task with a date and `in_calendar`, done ones for 30 days after their date, each with a `tt_hash` (FNV-1a of the body) in the private properties. Google's side is the calendar's events that carry `tt_task_id`. Missing or different hash: `POST` with the deterministic id, and on 409 `PUT` (409 also covers an event deleted on Google, whose id Google remembers); not in the plan: `DELETE` (404/410 count as gone); same hash: nothing. Events without `tt_task_id` (added by hand) are never touched. Nothing is remembered locally about what was pushed, so a restored backup or a half-finished push converges the same way.
   - **When**: 30 s after the daemon starts, 5 s after any database change (an edit, a sync, a fetch; debounced), every 15 minutes, and on "push now". Only while Google is signed in; signed out or switched off is a no-op with no requests. Failures: 429, rate-limit 403 and 5xx back off exponentially like `get_json` (5 tries); an event Google refuses is counted and the rest still go; status shows the first error.
   - **Two signed-in devices stay stable** because the event id is deterministic and both compute the same plan from synced tasks: the second sees matching hashes and sends nothing, and a race on one id ends in one 409 and an identical `PUT`. Before they have synced they may overwrite each other's version of a task; the id is the same so there is still one event, and the first reconcile after they converge settles it. No `If-Match`/etag: a 412 would only mean "another device wrote first", and the next reconcile reaches the same end state. (A real two-device run is untested.)
   - **Repeats: a window of single events, not an RRULE.** Decision, after reading plan/06, plan/18 and `recur.rs`:
     - The app has one recurrence engine (the `rrule` crate in the task's zone, with `fixed` and `after_completion` modes, COUNT/UNTIL handled in the core, and a completion moving the same task to the next date). Google's own expansion could drift from it (DST, BYSETPOS/zone edge cases) and has no way to say "repeat after completion", which only knows its next date.
     - A window reuses `Store::calendar`, so Google shows exactly what the app's calendar shows: later occurrences of fixed repeats up to 120 days ahead, only the next one for after-completion repeats, and the last 30 days of completed occurrences marked ✓. Completing an occurrence changes nothing for the others; only the finished one flips to ✓.
     - Cost: up to ~120 events for a daily task, and the window slides on the next reconcile (every 15 minutes at most). Each occurrence's id is the task's id plus `v` and its UTC start (`yyyymmddhhmm`), so it is stable while the occurrence stays put. Dragging the next occurrence to another time makes a new id (one delete, one create).
     - Not an open question in plan/11, so nothing to flag there; revisit if Google's event quota or the 15-minute slide bothers anyone.
   - **Edits made in Google** to those events are overwritten only when the task changes (the hash lives on the event, so an untouched task isn't re-sent); the page says it is one-way.
   - **What only a real sign-in can confirm**: that `calendar.app.created` lets a device create and write the "Tasks" calendar (and that `calendarList` returns it for the marker search), the 409 behaviour for an event deleted in Google's UI, `events.list` returning `extendedProperties.private` and the 2500 page size, and real rate-limit replies.
5. ✅ (code; **not tried against real Google**, see "Needs the user") **Android: events in on the phone** (2026-11-26).
   - **Why no refresh token:** Google Identity's `AuthorizationClient` (`play-services-auth` 22.0.0) keeps the grant inside Play services and hands out one-hour access tokens, silently, once the user agreed. So the phone has no client secret and no refresh token, and the desktop's loopback flow stays as it is.
   - `utre-google`: the token logic moved behind `session::Authorizer`. `LoopbackAuthorizer` is the desktop's (unchanged behaviour; `Session::new`/`sign_in` still work as before). `AndroidAuthorizer` (`android.rs`) caches the token in a `TokenStore` (`google-token.json` next to the database: app-private directory, mode 0600; a keystore wasn't cheap because Play services owns the real grant, the file holds only a one-hour token) and asks Kotlin through the `AccessTokenProvider` callback when it runs out or Google answers 401 (the refused token is handed back so Play services drops it). "Consent needed" signs the device out; a passing error (no network) does not. On Android the HTTP client trusts bundled roots (reqwest's platform verifier needs Java-side setup).
   - Phone service (`app/rust/src/google.rs`, `PhoneGoogle`): status, `sync_now` (same `sync_calendars` as the daemon), `sync_if_stale`, sign-out (forgets tokens and cache). Fetches: a 15-minute poll while the process lives, `kotlin::background_sync` after each WorkManager round (skipped when one succeeded within 14 minutes, so expedited jobs don't refetch), and `TaskDb.googleSyncIfStale(300)` when the calendar opens. Fetches tick the change stream, so the calendar reloads. The bridge's `googleStatus`/`googleSync`/`googleSignOut`/`gcalSelect`/`gcalEvents`/`gcalCalendars` are unchanged for Dart; they use the phone service when Kotlin installed it.
   - Kotlin (`google/GoogleAuth.kt`): implements `AccessTokenSource` (UniFFI callback) with silent `authorize`; `signIn(activity)` runs the consent screen (`startIntentSenderForResult`, result through `MainActivity.onActivityResult`) and hands the first token to `googleSignedIn`. Dart reaches it through the `utre/widget` channel (`googleSignIn` → `ok`, `cancelled`, `not_configured`, `error: ...`).
   - **Client id from config, never committed:** `utre.googleAndroidClientId` in `~/.gradle/gradle.properties`, `app/android/google.properties` (git-ignored), `-P`, or `UTRE_GOOGLE_ANDROID_CLIENT_ID`. It becomes manifest meta-data. Google finds an Android client by package name and signing-key SHA-1, so the id is only the switch: without it the Google page says "not set up in this build" and names what is missing.
   - UI: the Google page is now on the phone too (Soft style; `GoogleSource` seam so it is widget-tested: not set up, signed out, signed in, sign-out confirm, failed fetch). Google events are read-only in the phone's Day/Week/Month, as on desktop. The page asks for the same two scopes as the desktop.
   - **Needs the user (Google Cloud console):** create an OAuth client of type **Android** for package `dev.utre.utre` with the SHA-1 of the key that signs the APK (today the Arch laptop's debug key: `keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android`; the release key later needs its own client). Same project as the desktop client; the consent screen needs the calendar scopes and the user as a test user. Put the new client's id in `google.properties` and build.
   - **Not tested:** the consent screen, silent token refresh and a real fetch on the phone (they need that client). Tested: the Rust authoriser and phone service against the fake Google, the Dart page states, and (below) the release build.

## Open
- Schema v8 means an older build refuses a v8 database (per device, so only a concern if a DB file is copied between machines).
- **The app is unverified** (the user's call, 2026-11-26: fix later). Sign-in works now behind Google's "unverified app" warning (Advanced, then continue). Verification is Google's review process: https://support.google.com/cloud/answer/7454865. Check what it asks for the two scopes before starting; likely a verified domain (`utre.party` is live), the privacy policy and homepage already published, and a demo of the sign-in. Until then: the warning on every new device, and the 100-user cap (irrelevant here). Also check the consent screen is **In production**, or refresh tokens last 7 days.
- Tokens go in the keychain (libsecret on Linux, Keychain on macOS); check the crate and its version before use.
